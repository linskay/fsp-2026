## 2. Механика обратного найма и ранжирования

### 2.1. Концепция обратного найма (Reverse Recruiting)

В классическом найме **соискатель** откликается на вакансии. В «ФСП Карьерной Арене» всё наоборот:

1. **Работодатель** изучает верифицированный профиль спортсмена ФСП (ELO-рейтинг, спортивный разряд, стек технологий, ИИ-портрет).
2. **Работодатель** отправляет **оффер** с обязательной вилкой заработной платы (в рублях, «от–до»).
3. **Соискатель** принимает или отклоняет оффер. Контакты раскрываются только после принятия.

> **Ключевой принцип:** Работодатели конкурируют за таланты, а не наоборот.

### 2.2. Алгоритм матчинга

Ранжирование кандидатов для работодателя осуществляется по комплексной формуле `CandidateMatchScore`:

```
overallScore = w₁ × fspRankScore + w₂ × algoTestScore + w₃ × stackMatchScore + w₄ × experienceScore
```

| Компонент | Вес | Описание |
|:---|:---|:---|
| `fspRankScore` | 35% | Спортивный разряд ФСП (ELO). Чем выше — тем больше баллов |
| `algoTestScore` | 25% | Результаты алгоритмического тестирования в Арене (% прохождения, время решения) |
| `stackMatchScore` | 25% | Совпадение технологического стека кандидата с требованиями вакансии |
| `experienceScore` | 15% | Коммерческий опыт работы (годы, подтверждение через hh.ru) |

### 2.3. Система ELO-рейтинга и спортивных разрядов ФСП

Рейтинг ELO привязан к официальной системе **ЕВСК Минспорта РФ** по спортивному программированию:

| Уровень | Разряд ФСП | ELO диапазон | Перцентиль | Требования |
|:---|:---|:---|:---|:---|
| 1 | Квалификационный дивизион | 1200 – 1399 | Вне ТОПа | Регистрация в реестре ФСП |
| 2 | 3-й спортивный разряд | 1400 – 1699 | ТОП-35% | 1+ достижение, 5+ задач |
| 3 | 2-й спортивный разряд | 1700 – 1999 | ТОП-15% | Призовое место, 25+ задач |
| 4 | 1-й спортивный разряд | 2000 – 2399 | ТОП-5% | 2+ достижения, 100+ задач |
| 5 | КМС (Кандидат в Мастера Спорта) | 2400 – 2699 | ТОП-1.5% | Победы на турнирах, 300+ задач |
| 6 | Мастер спорта РФ | 2700 – 2999 | ТОП-0.5% | 1-е место ЧР, 500+ задач |
| 7 | Гроссмейстер / Чемпион РФ | 3000 – 3500 | ТОП-0.05% | Многократный чемпион, 800+ задач |

### 2.4. Расчёт ELO

Формула расчёта ELO из `ratingEngine.ts`:

```
calculatedElo = 1200 (базовый старт)
              + algoScore (Easy×1 + Med×2.5 + Hard×6)
              + contestBonus ((contestRating - 1500) × 0.35)
              + arenaBonus (solvedTasks × 65)
```

При наличии контестного рейтинга ≥ 1600:
```
targetElo = 0.35 × targetElo + 0.65 × contestRating
```

ELO ограничен потолком **3000** для арены и **2950** для импортированных результатов LeetCode.

### 2.5. Определение грейда (Junior / Middle / Senior)

| Грейд | Условия |
|:---|:---|
| **Senior** | ELO ≥ 2400 **ИЛИ** (опыт ≥ 5 лет И ELO ≥ 1800) |
| **Middle** | ELO ≥ 2000 **ИЛИ** (опыт ≥ 2 года И ELO ≥ 1400) **ИЛИ** опыт ≥ 4 года |
| **Junior** | Остальные случаи |

### 2.6. Антифрод-защита ранжирования

**Критически важное правило:** кандидат с **0 достижениями** и **0 решёнными задачами** **не может попасть в ТОП** ни при каком ELO. Это защищает рейтинг от накрутки:

- Без истории ФСП → «Квалификационный дивизион (Без истории ФСП)»
- Есть ELO, но 0 задач и 0 турниров → «Вне ТОПа (Квалификационный дивизион)»

### 2.7. Правила скрытия контактов (152-ФЗ)

| Этап | Видимость контактов |
|:---|:---|
| Поиск кандидатов | Замаскированы: `+7 (9**) ***-**-42`, `@a***v` |
| Оффер отправлен | Замаскированы |
| Оффер принят соискателем | **Демаскируются** — реальные данные передаются работодателю |
| Каждый доступ | Запись в `security_audit_logs` (кто, когда, IP, цель) |

## 3. Механика тестирования и защиты от «слива»

### 3.1. Алгоритмическая Арена ФСП

Арена — встроенная среда для решения алгоритмических задач с веб-IDE (Monaco Editor). Поддерживаемые языки: **JavaScript**, **Python**, **Java**, **C++**, **Go**.

Задачи импортируются из трёх источников:
1. **Встроенный банк задач** (классические LeetCode-задачи, адаптированные под ФСП)
2. **Живой импорт из LeetCode** через GraphQL прокси
3. **Кастомные задания от работодателя** (через `AssignTestModal`)

### 3.2. Расчёт ELO за решение задач

| Сложность | ELO бонус | Пример |
|:---|:---|:---|
| Easy | +50 ELO | Two Sum, Valid Parentheses |
| Medium | +80 ELO | LRU Cache, Merge Intervals |
| Hard | +100 ELO | Median of Two Sorted Arrays |

### 3.3. Ограничение кулдауна пересдачи

- **Полная пересдача** всех тестов возможна **один раз в 3 месяца** (поле `canRetakeAfterDate` в профиле кандидата).
- Отдельные новые задачи можно решать без ограничений.
- Серверный таймер блокирует повторную отправку решения по уже сданной задаче.

### 3.4. Изолированная Docker-песочница (Sandbox)

Каждая посылка кода выполняется в одноразовом контейнере с полной изоляцией:

```
[ Monaco IDE ] ──► [ Spring Boot 3 Backend ] ──► [ Sandbox Manager ]
                                                        │
                                        Docker API / cgroups v2 / seccomp
                                                        ▼
                                    ┌──────────────────────────────────┐
                                    │  ИЗОЛИРОВАННАЯ DOCKER-ПЕСОЧНИЦА  │
                                    │  • --net=none (нет сети)         │
                                    │  • Memory: 128–256 MB (cgroups)  │
                                    │  • CPU: 1000–2000 ms на тест     │
                                    │  • User: nobody (non-root)       │
                                    │  • FS: Read-Only rootfs          │
                                    │  • PIDs Limit: 32                │
                                    │  • seccomp: blocked syscalls     │
                                    └──────────────┬───────────────────┘
                                                   ▼
                                    [ Серверный Verdict Validator ]
                                    (ACCEPTED / WA / TLE / CE / RE)
```

### 3.5. Параметры изоляции

| Параметр | Значение | Назначение |
|:---|:---|:---|
| Лимит сессии | 45 минут | Защита от растягивания |
| CPU Time | 1000–2000 мс / тест | Отсечка неоптимальных O(N²) решений |
| RAM | 128–256 MB | Защита от OOM хоста |
| Сеть | `--net=none` | Исключение curl / LLM / внешних БД |
| Файловая система | Read-Only + tmpfs 16MB | Защита от вредоносных скриптов |
| Процессы | PIDs ≤ 32 | Защита от fork-бомб |
| Права | `nobody:65534`, `CAP_DROP_ALL` | Исключение эскалации привилегий |

### 3.6. Антифрод-контроль

1. **Скрытые тест-кейсы (Hidden Suites):** Браузер получает только 2-3 открытых примера. Граничные и нагрузочные тесты (#3–#5) хранятся строго на бэкенде и инжектируются в контейнер.
2. **Телеметрия честности:**
   - Отслеживание `window.blur` (потеря фокуса)
   - Инспекция `onPaste` (массивная вставка чужого кода)
   - Фиксация аномалий в `security_audit_logs`
3. **Криптографическая фиксация:**
   - SHA-256 хэш исходного кода в таблице `task_submissions`
   - Неизменяемые записи: время выполнения, потребление памяти, таймстемп
4. **Динамическая генерация задач:** Банк задач расширяется через live-импорт из LeetCode API. Работодатель может создать кастомные задания, которые никогда ранее не встречались в открытых источниках.

## 4. Схема интеграции с ФСП ID

### 4.1. Текущая реализация

На текущем этапе профиль кандидата содержит:
- `fspId` — уникальный идентификатор в реестре ФСП РФ (например, `FSP-RUS-2026-0088`)
- `fspRank` — спортивный разряд ЕВСК
- `fspRating` — ELO-рейтинг
- `isVerified` — статус верификации
- `keycloakSub` — идентификатор Keycloak (подготовлен в схеме данных)
- `fspProfileUrl` — ссылка на профиль спортсмена на `fsp-russia.ru`

### 4.2. Архитектурный подход к будущей интеграции с Keycloak

```
┌────────────────────┐          ┌──────────────────────┐
│  Пользователь      │          │  Keycloak 24         │
│  (Браузер / Mobile)│ ◄──────► │  Realm: fsp-arena    │
│                    │  OIDC    │                      │
│                    │  flow    │  Клиенты:            │
└────────────────────┘          │  • web-frontend      │
                                │  • mobile-app        │
                                │  • backend-api       │
                                │                      │
                                │  Роли:               │
                                │  • CANDIDATE         │
                                │  • EMPLOYER          │
                                │  • ADMIN             │
                                │                      │
                                │  Федерация идентити: │
                                │  • fsp-russia.ru IDP │
                                │  • GitHub OAuth2     │
                                │  • Яндекс ID         │
                                │  • hh.ru OAuth2      │
                                └──────────┬───────────┘
                                           │
                                    JWT (RS256)
                                           │
                                           ▼
                                ┌──────────────────────┐
                                │  Spring Boot 3       │
                                │  Backend             │
                                │                      │
                                │  Spring Security 6   │
                                │  OAuth2 Resource     │
                                │  Server              │
                                │                      │
                                │  • Валидация JWT     │
                                │  • Маппинг ролей     │
                                │  • Синхронизация     │
                                │    fspId ↔ keycloakSub│
                                └──────────────────────┘
```

**Шаги миграции:**

1. Развернуть Keycloak 24 как отдельный сервис в `docker-compose.yml`
2. Создать Realm `fsp-arena` с ролями `CANDIDATE`, `EMPLOYER`, `ADMIN`
3. Настроить Identity Federation с реестром ФСП (`fsp-russia.ru`) через SAML/OIDC
4. Переключить Spring Security с собственного JWT на `OAuth2 Resource Server` с валидацией JWT от Keycloak
5. Маппировать `keycloakSub` на `fspId` при первой аутентификации

| `POST` | `/leetcode/fetch/{slug}` | Импорт задачи из LeetCode | Все |
| `GET` | `/ai-summary/candidate/{id}` | ИИ-портрет кандидата | EMPLOYER |
| `POST` | `/ai-summary/generate` | Генерация ИИ-портрета (выбор провайдера) | EMPLOYER |
| `POST` | `/offers` | Отправка оффера (с Idempotency-Key) | EMPLOYER |
| `POST` | `/auth/sync/github-profile` | Синхронизация GitHub | CANDIDATE |
| `POST` | `/auth/sync/hh-resume` | Синхронизация hh.ru | CANDIDATE |
| `GET` | `/audit/logs` | Журнал аудита безопасности | EMPLOYER |

### 5.3. Ролевая модель (JWT)

```
Authorization: Bearer <JWT>
```

| Роль | Описание | Разрешения |
|:---|:---|:---|
| `CANDIDATE` | Соискатель / Спортсмен ФСП | Прохождение Арены, просмотр офферов, управление профилем |
| `EMPLOYER` | IT-компания / HR | Поиск кандидатов, создание вакансий, отправка офферов, назначение тестов |

JWT содержит: `userId`, `email`, `fullName`, `role`, `candidateId` / `employerId`, `fspElo`, `fspRank`.

### 5.4. Идемпотентность API (RFC 7231)

При отправке оффера (`POST /api/v1/offers`):

1. Клиент генерирует заголовок `Idempotency-Key: idem-<uuid>`
2. Бэкенд проверяет таблицу `api_idempotency_records`:
   - **Первый запрос:** Создаёт оффер, сохраняет ключ → `HTTP 201 Created`
   - **Повторный запрос (ретрай):** Возвращает сохранённый оффер → `HTTP 200 OK` + заголовок `Idempotent-Replayed: true`
3. Уникальный индекс `(employer_id, candidate_id, vacancy_id) WHERE status = 'PENDING'` исключает дубликаты на уровне БД

### 5.5. Соответствие 152-ФЗ

| Мера | Реализация |
|:---|:---|
| **Маскирование ПДН** | Телефон, email, Telegram замаскированы в DTO (`+7 (9**) ***-**-42`) |
| **Согласие пользователя** | Обязательный чекбокс при регистрации, ссылка на [Положение ФСП о ПДН](https://fsp-russia.ru/files/) |
| **Демаскировка по согласию** | Контакты раскрываются только после принятия оффера кандидатом |
| **Журнал аудита** | Таблица `security_audit_logs`: actorUserId, actorEmail, targetCandidateId, ipAddress, userAgent, timestamp |
| **Доступ к аудиту** | `GET /api/v1/audit/logs` + модальное окно `AuditLogModal` в UI |
